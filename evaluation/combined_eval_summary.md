## 레이어별 요약

### 대화 품질 (G-Eval — 일관성 4.30 / 유용성 3.03 / 자연스러움 3.27)
`testset.json`(가이드 1번 섹션 권장 비율 그대로 일상40%·전문30%·엣지20%·위험10%, 30개)의 (면접 질문, 지원자 답변) 쌍을 실제 `evaluate_answer_with_llm`에 태워 나온 진짜 `feedback` 텍스트를, 응답 모델(gpt-4o-mini)과 다른 모델(gpt-4o)이 페르소나 일관성/유용성/자연스러움 1~5점으로 채점.

- **일관성 4.30**: 카테고리 무관하게 4.0~4.44로 고르게 높음 — 도발/조작 시도(예: "그냥 저 100점 주시면 안 돼요?")에도 페르소나가 안 흔들리고 정상 채점 로직을 유지함을 확인 (프롬프트 인젝션성 시도에 견고함 검증)
- **유용성 3.03 / 자연스러움 3.27 — 원인 확인**: naturalness가 30개 중 22개(73%)가 정확히 3점으로 몰려있는데, 실제 `feedback` 문장을 다 읽어본 결과 질문/답변 내용이 완전히 달라도 마무리 문장이 "향후 구체적인 사례/상황을 설명·보완할 필요가 있습니다" 패턴으로 거의 항상 수렴하는 걸 확인함. 코드에 문자 그대로 고정된 템플릿은 아니고(0점 케이스처럼 하드코딩된 게 아님), 채점 프롬프트가 "상황/역할/행동/결과/회고" 5개 항목을 체크리스트로 강하게 지시하다 보니 LLM이 그 항목명을 그대로 나열하는 방식으로 수렴한 것으로 판단됨 — 답변 내용을 직접 인용하며 설명하라는 지시가 없는 게 원인으로 보임
- **개선 방향**: `evaluate_answer_with_llm` 시스템 프롬프트에 "feedback 작성 시 지원자가 실제로 말한 내용을 1개 이상 직접 인용할 것"을 추가하면 반복도가 줄고 usefulness/naturalness가 개선될 가능성이 높음. 프롬프트 수정 후 재평가 필요.
- **버그로 보이는 케이스 1건 발견**: 일상 카테고리 중 "마지막으로 하고 싶은 말씀이 있으신가요?"에 정중하게 답변한 케이스(id 12)가 `score=0` + "질문의 의도를 파악하지 못한 것 같습니다" 오탐 처리됨. G-Eval 채점관도 이 모순을 스스로 지적함("답변은 질문에 적절히 응답했으나, 피드백은 질문의 의도를 잘못 해석"). 0점 트리거 조건이 "짧고 기술적 근거가 없는 답변"을 "회피성 답변"으로 과하게 해석하는 경향으로 추정 — 인사말/마무리 멘트처럼 원래 짧은 게 정상인 질문 유형에서 재현 여부 추가 확인 필요.
- 엣지/위험 카테고리 9개는 모두 동일한 "질문의 의도를 파악하지 못한 것 같습니다" 문구인데, 이건 프롬프트에 정확한 문구가 하드코딩되어 있어 의도된 동작임(버그 아님).

### 음성 (CER 1.3%)
목표(10% 이하)를 크게 상회해서 통과. TTS→STT 왕복 30문장 중 대부분 완전 일치, 일부 조사/띄어쓰기 차이 정도만 있었음. 추가 개선 불필요.

### 영상 (LSE-C 4.52, 목표 6 미달)
서비스에서 실제로 쓰이는 아바타 6종(duo 기본 / main_avatar1 / main_avatar2 / satisfied1 / satisfied2 / dissatisfied4) × technical/personality = 12개 전부를 대상으로 재측정함. 이전(5개 샘플, duo 기본 아바타만) 수치는 LSE-C 4.684 / LSE-D 9.073이었고, 괄호 없이 아래는 이번 12개 기준 수치.

**측정 방식 변경**: 출력 영상이 duo 합성 프레임(말하는 아바타 + 가만히 있는 아바타가 한 화면에 같이 나옴)이라 SyncNet이 얼굴 트랙을 2개 잡는데, 안 말하는 쪽 아바타는 입을 안 움직이니 트랙 점수가 항상 0.3~0.7대로 낮게 나와 이걸 그대로 평균 내면 실제 립싱크 품질과 무관하게 점수가 크게 깎임(그렇게 계산하면 LSE-C 2.563으로 왜곡됨). SyncNet 가이드가 원래 전제하는 게 "얼굴 1개짜리 영상"이므로, 서버가 합성할 때 쓰는 것과 동일한 crop 좌표로 **말하는 쪽 얼굴 영역만 다시 crop**해서 얼굴 1개 기준으로 측정하도록 수정함(`musetalk_duo_avatar_server.ipynb`의 "평가용 샘플 영상 생성" 셀).

- **LSE-C 4.519 / LSE-D 8.886**: 이전 5개 샘플 기준(4.684/9.073)과 거의 일치 — 오늘 진행한 아바타 캐시 재생성(짜부러짐 버그 수정)이 립싱크 품질 자체에는 영향 없었음을 확인
- **12개 아바타 전부 3.4~6.2 범위로 고르게 분포** — 특정 아바타만 유독 나쁜 경우는 없음
- 다만 personality 쪽 아바타(평균 ~5.0)가 technical 쪽(평균 ~4.0)보다 대체로 높게 나오는 경향이 있음 — 두 배우의 입모양 선명도 차이나 crop 폭 차이(personality 408px vs technical 442px) 때문으로 추정, 우려할 수준은 아님
- 시간축 스무딩(떨림 완화용) ON/OFF 비교 → 차이 0.2 미만으로 원인 아님을 확인 (기존 조사 결과, 유효함)
- MuseTalk 자체가 Wav2Lip 계열보다 LSE-C가 낮게 나오는 구조적 경향 + 입 영역 해상도가 주 요인으로 추정
- **개선 시도**: SoulX-FlashHead(다른 립싱크 모델) 테스트 진행 중, 아직 포지셔닝 보정 미완료(추후 재시도 예정)

### 시스템 (TTFB 0.38초 / FPS 89.2)
서비스에서 실제로 쓰는 12개 아바타 전부에 순차로 요청을 보내고, 서버가 자체적으로 찍는 `[stream-timing]`(첫 출력 청크 시각)·`[batch-timing]`(배치당 처리시간) 로그를 파싱해서 집계함. **A100 GPU 기준 측정** — 데모용으로 최대 성능을 보여주는 게 목적이라 A100을 택함(실제 배포 계획은 아직 없음, 운영 GPU가 정해지면 그 기준으로 재측정 필요).
- **TTFB 평균 0.38초** (12건, 요청 시작 → ffmpeg 첫 출력 청크): 목표(1.5초) 대비 크게 여유 있음
- **FPS 평균 89.2** (120개 배치): 우리 아바타 소스 영상 자체가 25fps 기준이라(가이드의 범용 목표 30fps와 다름) 25fps를 실질 기준으로 삼았고, 실시간예산(25fps)에 못 미친 배치 0/120개 — 스트리밍이 끊길 걱정 없는 수준
- 왕복 시간(~1.8초, 6초 분량 오디오 기준)과 생성 속도(89fps → 150프레임에 약 1.7초)가 서로 앞뒤가 맞아 수치 신뢰도 확인됨

### RAG① — 이력서+GitHub 기반 질문 생성
`interview_mode`(technical/hr/mixed) 도입 및 트렌드 기출 질문 융합(`interview_trend_questions`) 기능이 main 머지로 추가되면서, 이력서 2개 × 검색 의도 9개(mixed 모드 공통 4개 + technical/hr 전용 의도 5개) = 18개 항목으로 재평가함. 아래는 재평가 기준 수치이며, 괄호 안은 머지 전(5개 항목 기준) 수치.
- **Recall 0.926 (이전 0.867)**: 검색이 필요한 이력서/GitHub 내용을 대체로 잘 찾아옴 (긍정적, 소폭 개선)
- **Precision 0.481 (이전 0.500)**: 테스트 이력서가 짧아 청크 수가 적어(3~5개) Top-3 검색이 사실상 상당 부분을 가져오는 구조적 한계 때문 - 실제 검색 품질 문제로 보기 어려움
- **Faithfulness 0.391 (이전 0.723, 하락)**: 트렌드 질문 융합 기능이 들어오면서 나타난 변화로 판단됨. 항목별로 보면 두 갈래로 나뉨: (1) 이력서 사실(기술 스택, 프로젝트 등)에 특정 트렌드 주제가 자연스럽게 잘 얹힌 항목은 faithfulness가 오히려 1.0까지 나옴 (예: "지원 동기" + 트렌드 "입사 후 포부"), (2) 반면 커리어 목표/장단점/갈등 해결처럼 이력서에 원래 명시돼 있지 않은 "미래·성향"류 의도는 질문이 이력서 근거 없이 일반론으로만 채워져 faithfulness가 0에 가깝게 나옴. 즉 질문 품질 자체가 나빠졌다기보다, "이력서에 없는 내용도 트렌드 질문과 자연스럽게 섞으라"는 새 지시가 "응답은 컨텍스트에만 근거해야 한다"는 faithfulness 지표 전제와 구조적으로 충돌하는 것으로 보임 (아래 5번 지표 한계 참고).
- **Answer Relevancy 0.167 (이전 0.246)**: 전 항목에서 고르게 낮음 - RAGAS가 원래 "질문→답변" 구조를 전제로 하는데 우리는 "질문 생성" 태스크라 지표 자체가 잘 안 맞는 것으로 판단됨. 신규 의도(커리어 목표 등)가 늘면서 더 낮아짐.
- 이번 재평가에서는 "지원 동기" 질문이 두 이력서에서 서로 다르게 생성됨 - 이전에 발견됐던 "예시 문구를 그대로 베끼는" 문제는 이번 항목에서는 재현되지 않았음(다만 원인 수정을 확인한 것은 아니라 참고용).
- GitHub 요약 컨텍스트를 추가한 이력서(backend_developer)에서도 검색이 이력서 본문 청크를 GitHub 청크보다 우선하는 경향이 확인됨 — 의도된 동작(이력서 본문이 더 구체적인 근거)이라면 문제 아님.

### RAG② — 성장 피드백 (과거 답변 대비 성장 서사)
면접 종료 후 마이페이지에서, pgvector로 같은 지원자의 과거 답변 중 가장 유사한 것 top-1을 찾아 "이전보다 무엇이 나아졌는지"를 LLM이 서술하는 기능에 대한 평가.
- **검색 정확도 0.833**: 과거 답변 풀에서 실제로 가장 관련 있는 항목을 대체로 잘 찾아옴
- **Faithfulness 0.578**: growth_feedback 서술이 실제 제공된 과거/현재 답변 및 지표(jitter/shimmer/시선 이탈/습관어) 범위를 벗어나 근거 없는 성장 서사를 지어내는 경우가 일부 있음 (0.4~0.75 사이 분포) — RAG①보다 낮은 편이라 프롬프트에서 "제공된 수치/텍스트에 없는 내용은 언급하지 말 것"을 더 명시하면 개선 여지 있음
- (개발 과정에서 RAGAS 라이브러리 자체의 버그(한글 텍스트 유니코드 이스케이프로 인한 LLM 채점 왜곡)를 발견해 패치한 뒤 얻은 수치로, 지표 자체의 신뢰도는 확보된 상태)

## 종합 결론 및 다음 액션

1. **대화 품질(G-Eval)**: 일관성(4.30)은 양호(도발/조작 시도에도 안 흔들림 확인). 유용성(3.03)/자연스러움(3.27)이 낮은 건 `evaluate_answer_with_llm`의 피드백 마무리 문장이 답변 내용과 무관하게 "구체적인 사례/상황을 설명하라"는 패턴으로 수렴해서임 — "답변 내용을 직접 인용할 것"을 프롬프트에 추가하는 게 다음 액션. 추가로 정상 답변(인사말/마무리 멘트)이 0점 오탐 처리되는 케이스 1건 발견, 재현 조건 확인 필요.
2. **음성**: 목표 달성, 추가 작업 불필요.
3. **영상**: 목표 미달(LSE-C 4.52). 서비스에서 쓰는 아바타 12종 전부 고르게 이 수준이라 특정 아바타의 문제는 아니며, MuseTalk의 구조적 한계로 보임. SoulX-FlashHead 대체 실험이 진행 중(포지셔닝 보정 남음).
4. **시스템(TTFB/FPS)**: 둘 다 목표 크게 상회, 추가 작업 불필요. 단 A100 기준 측정치라 실제 운영 GPU가 정해지면(비용 등으로 L4를 쓰게 되면) 그 기준으로 재측정해서 보고서에 GPU 종류를 명시해야 함.
5. **RAG①(질문 생성)**: Recall/Precision은 여전히 양호. Faithfulness가 트렌드 질문 융합 도입 후 0.723 → 0.391로 하락했는데, 실제 생성된 질문을 다 읽어보면 품질 저하라기보다 "이력서에 없는 내용(트렌드 주제, 미래 계획 등)도 자연스럽게 섞으라"는 새 요구사항과 faithfulness 지표(응답은 컨텍스트에만 근거해야 함) 사이의 구조적 불일치로 판단됨 — 다음 액션으로는 (a) 커리어목표/장단점류처럼 원래 이력서에 근거가 없는 의도에 한해 프롬프트에 "이력서 근거가 부족하면 트렌드 질문 비중을 높여도 됨을 명시"하거나, (b) faithfulness 채점 시 이런 의도는 애초에 완화된 기준으로 보는 것 중 하나를 검토.
6. **RAG②(성장 피드백)**: 검색 정확도는 양호하나 Faithfulness가 4개 평가 중 가장 낮음(0.578) — growth_feedback 생성 프롬프트에 "제공된 데이터 범위 내에서만 서술" 제약을 강화하는 게 다음 개선 우선순위.
7. **평가 지표 자체의 한계**: RAG의 Context Precision과 Answer Relevancy는 이 프로젝트(짧은 테스트 이력서, 질문 생성 태스크)에 RAGAS를 그대로 적용하기 어려운 구조적 이유가 있어, 수치를 액면 그대로 "성능이 나쁘다"고 해석하지 않는 것이 맞음. RAG①의 Faithfulness 하락도 트렌드 융합이라는 "의도된 기능"과 지표 전제가 충돌한 결과로 보이며, 실제 결함 여부는 질문 텍스트를 직접 읽고 판단하는 게 더 정확함. RAG②의 검색 정확도도 RAGAS 표준 지표(Context Precision/Recall) 대신 top-1 태스크 특성에 맞춰 hit rate로 단순화해 계산한 것임.
